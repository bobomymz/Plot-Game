# 休息节点 × 整理整理入口 改造报告

日期：2026-09-26
需求：给所有休息节点加「整理整理」入口，玩家休息时能就地整理背包。

## 结论

**20 个休息节点全部加上了入口，并顺手堵住了 3 类"反复整理即可刷"的漏洞**（这些漏洞是"加入口"这个动作本身引入的，不是既有问题）。

- 入口数：20 / 20（改造前 0 / 20）
- 自检：`node tools/rest_tidy_selftest.js` → **155 通过 / 0 失败**（含 13 条"不守卫必重复结算"的对照组）
- 完整回归全绿（见文末）

## 1. 休息节点是怎么定义的

不是按名字（"休息"/"歇脚" 各种叫法都有），**按代码**：`onEnter` 里调用 `utils.js` 的 `restRecover(vars, n)` 的场景。全库共 **20 个**。

> 判定靠源码扫描而非场景名——`理发店-休息`、`图书馆-小憩`、`三林安居苑-7号楼-天台-歇脚`、`建平-济美楼-4F-音乐教室-听音乐` 名字完全不同，但都是休息节点。
> 工具：`node tools/rest_tidy_audit.js`（列出全部节点 + 是否已有入口 + 既有入口的重复结算风险）。

## 2. 改动内容

### 2.1 新增两个通用工厂（`story/utils.js`）

```js
function restTidyChoice(id) {          // 休息场景 choices 里加这一条即可
  return {
    showCondition: "itemCount > 0",
    text: "🎒整理一下物品",
    nextScene: "整理整理",
    effect: { set: { positionAfterOperation: id, _restTidyReturn: true } }
  };
}
function restTidyGuard(vars) {         // 休息场景 onEnter 开头调用
  if (!vars._restTidyReturn) return null;
  vars._restTidyReturn = false;
  return {};
}
```

沿用建平章已有的写法惯例（`showCondition: "itemCount > 0"` + 🎒 图标 + `positionAfterOperation` 指回本场景），20 处不再各写一遍。

### 2.2 新增变量（`story/core.js` `_variables`）

`_restTidyReturn: false` —— 布尔标记，无需 `_caps`；新增变量按约定 **未 bump `SAVE_VERSION`**（旧档由 `fillMissingDefaults` 补初值）。

### 2.3 ⚠ 为什么入口必须配 guard（本次真正的技术点）

`整理整理` 的唯一出口是 `nextScene: "{positionAfterOperation}"`，也就是**回到入口场景** —— 回到休息节点会**再跑一次 `onEnter`**。20 个休息节点里有 13 个的 `onEnter` 带副作用，不拦住就是纯刷子：

| 漏洞 | 场景 | 反复"整理→返回"的后果 |
| --- | --- | --- |
| 重复推进时间 | 13 个（5~30 分钟不等） | 白嫖时间代价 / 反过来被饥饿时钟白白惩罚 |
| **重复甩追兵** `chasedByZombies -1` | 新达汇-1F味千拉面-休息 / -没吃的 | **尸潮等级刷到 0**（原设计：只有"进入休息"才甩一次） |
| **重复消耗 NPC 口粮次数** `_zhaoGuangchengFoodGiven++` | 益丰大药房-匀口饭吃 | 赵广成"最多匀 2 次"的门控被绕过，且次数白扣 |
| **重复过夜跳天** `dd++`、`hh=7:30` | 理发店-休息（夜间分支） | **一天变两天**，直接跳时间线 |

这些都属于"加入口引入的漏洞"，不是既有 bug —— 所以一并修了，未当作平衡项改动（没有削弱任何原本的收益，只是让"整理后回到原地"不重复发放）。

## 4. 自检脚本（可重跑）

`tools/rest_tidy_selftest.js` —— 155 断言，五段：

- **S1** 每个休息节点都有入口，且 `positionAfterOperation` 指回本场景（防从整理退出后掉进别处）
- **S2** 从整理返回：`时间不推进 / 尸潮不重复甩 / 口粮次数不重复消耗 / 不重复跳天 / _restTidyReturn 已清零`
- **S3** 标记清零后正常进入仍照常结算（守卫不能吃掉正常收益）
- **S4** `整理整理` 自身出口健康（`{positionAfterOperation}` + 「不丢，谢谢」）
- **S5 对照组** 13 个 A 类节点"无标记进入确实会推进时间" —— 证明 S2 的 0 推进是守卫拦下来的，不是本来就不推进（防假绿）

## 6. 遗留 / 待办

1. **既有（非休息）整理入口的同类风险：4 处，只有 1 处真的有副作用**
   - `全家便利店-员工通道`（全家和公交站.js:454）：`onEnter` 有 `updateTime(3)`，整理返回会多花 3 分钟。轻微，且它的入口只在背包满时出现（"背包满了，先整理一下"），多花的 3 分钟可解释为整理耽误的时间 —— **要不要加 guard 由作者定**。
   - `安盛街中段` / `安盛街西侧` / `三林安居苑-小广场`：`onEnter` 只有 `showZombies=true`、`showRain=true`、`currentPos=…` 这类幂等 set，重复执行**无影响**，不用管。
   - 扫描器已内置在 `tools/rest_tidy_audit.js` 第 4 段，以后新增整理入口会自动列出风险。

2. **U 盘工作区会脏读**（本次踩到，值得记一笔）：工作目录在移动盘上，`git stash pop` 之后立刻跑脚本，读到的是未落盘的中间状态 ——
   表现为 `node --check` 报一个**实际不存在**的语法错误（`},,`）、`condition_audit` 打印 `执行失败 story/建平中学.js` 却仍然输出"0 处"（**假绿**）、`lint` 报一个其实存在的图片 404。
   **判据**：任何审计脚本输出里出现 `执行失败 <文件>` 都**必须**当回归失败处理，别只看末尾的 0。
   **做法**：大批量写入后先 `node --check` 全部 story 文件，再跑回归。
