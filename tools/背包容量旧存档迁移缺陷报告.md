# 背包容量「旧存档迁移」缺陷报告

> 日期：2026-09-24　触发场景：仁济南院，携带 帆布袋 + 轿车钥匙 + 手电筒 + 水瓶（空）
> 复现脚本：`node tools/bag_migration_repro.js`（期望「9 通过 / 6 BUG」，退出码 0）
> 相关文件：`story/core.js`（`_variables` / `_reactive.computed` / `整理整理`）、`engine.js`（`fillMissingDefaults` / `refreshComputed` / `SAVE_VERSION`）

---

## 一、结论（先说根因）

**这不是拾取闸门写错了，是 09-21 那次背包体系改造没有配套做存档迁移。**

`bagVolume` 从「可写的普通变量」变成了「派生值 `3 + _bagTier + _bagExtra`」，但 `SAVE_VERSION` 始终是 1（自 09-09 未变），于是**09-21 之前的旧档被照常加载**。迁移时 `_bagExtra` 只能被填成默认值 **0**，而不是按 `hasBag: true` 补成 **1**：

| 环节 | 玩家以为 | 引擎实际 |
|---|---|---|
| 容量 | 4（帆布袋 +1） | **3**（`_bagExtra` 被填 0） |
| 再捡一件 | 可以 | **不行**（`itemCount 3 < bagVolume 3` 为假） |
| 丢下帆布袋后 | 容量回到 3 | **`_bagExtra = -1`，容量掉到 2** |

`-1` 不是"另外冒出来的 bug"，它是**结果**：一个只被减过、从没被加过的计数器。

新开局**不会**出现这个问题——已用不变量验证（见下）。

---

## 二、复现（真实引擎无头跑通，数字可重跑）

```
=== 1) 新开局：不变量 hasBag=true ⇒ _bagExtra>=1（-1 不可达） ===
     初始        {"bagVolume":3,"_bagExtra":0,"hasBag":false}
     拾取帆布袋  {"bagVolume":4,"_bagExtra":1,"hasBag":true}
     丢下帆布袋  {"bagVolume":3,"_bagExtra":0,"hasBag":false}
   ok    初始：容量 3 / _bagExtra 0
   ok    拾取后：容量 4 / _bagExtra 1
   ok    丢弃后：容量 3 / _bagExtra 回到 0（新开局不会变负）
   ok    帆布袋拾取不占 itemCount（附件语义）——玩家 3 件占格物品 + 帆布袋 = itemCount 3

=== 2) 旧档（f9888a5 之前）：hasBag=true + bagVolume=4，无 _bagTier/_bagExtra ===
     迁移前（存档里存的）  {"bagVolume":4,"itemCount":3,"hasBag":true}
     迁移后（补默认值+重算）{"bagVolume":3,"_bagExtra":0,"_bagTier":0}
   BUG   容量 4 → 3：静默掉 1 格（_bagExtra 被填成 0，而不是 1）
   BUG   itemCount 3 < bagVolume 3 = false → 玩家『还能再捡一个』的判断落空（预期 true）
   ok    「丢下帆布袋」对旧档可见（showCondition=hasBag 为 true）——所以玩家点得到

=== 3) 旧档玩家点「丢下帆布袋」→ _bagExtra 减到 -1 ===
     丢帆布袋后      {"bagVolume":2,"_bagExtra":-1,"hasBag":false,"itemCount":3}
     再丢车钥匙后    {"bagVolume":2,"itemCount":2,"canPick":false}
   BUG   _bagExtra = -1 ← 控制台看到的 -1（应为 0）
   BUG   再丢钥匙后 itemCount 2 < bagVolume 2 = false → 仍捡不了，与实测一致

=== 4) 旧档是双肩包 / 书包时同样掉容量（同一根因的另一面） ===
     旧档有双肩包  {"旧容量":4,"迁移后":3}
     旧档有书包    {"旧容量":5,"迁移后":3}
   BUG   双肩包档：应 4，实际 3（掉 1）
   BUG   书包档：应 5，实际 3（掉 2）
```

第 3 组的两个数字与你描述的现象逐项吻合：丢袋后 `_bagExtra = -1`；再丢一件后 `itemCount 2 < bagVolume 2` 仍为假。

## 三、根因链（代码位置）

1. **改造前**（`f9888a5^`，即 09-21 13:00 之前）
   ```js
   bagVolume: 3,      // 可写的普通变量
   hasBag: false,     // 「是否有背包（bagVolume+1）」—— 帆布袋 / 双肩包 / 书包**共用这一个标志**
   // 拾取：set:{hasBag:true}, add:{bagVolume:1}      丢弃：set:{hasBag:false}, add:{bagVolume:-1}
   ```
   注意：旧档里 `bagVolume` 是**存了真实数字的**（帆布袋/双肩包档 = 4，书包档 = 5）。

2. **改造后**（`f9888a5`，09-21 13:00 起，`story/core.js:357`）
   ```js
   bagVolume: function(v) { return 3 + (v._bagTier || 0) + (v._bagExtra || 0); },
   ```
   `hasBag` 被收窄成「帆布袋」；双肩包 / 书包改走 `_bagTier`。拾取端与丢弃端同一次提交一起改了（没有"半改造"窗口）。

3. **漏掉的一环**：`SAVE_VERSION` 没有跟着动。
   ```
   git show f9888a5^:engine.js  →  SAVE_VERSION = 1
   git show f9888a5:engine.js   →  SAVE_VERSION = 1
   ```
   而 `loadSave()`（`engine.js:1394`）只在 `saved.version !== SAVE_VERSION` 时弃档 —— 相等 → 旧档照常进入 `applySave`。

4. **迁移函数救不了它**（`engine.js:1346` `fillMissingDefaults`）：
   它只会「**补缺失键的初值**」——`_bagExtra` 的初值就是 `0`。它**没有能力**从 `hasBag: true` 反推 `_bagExtra` 应该是 1。于是 +1 静默蒸发。

5. **`-1` 的出口**（`story/core.js:770-773`）：
   ```js
   { showCondition: "hasBag",
     text: "丢下帆布袋",
     effect: updateTime(1, { set : { hasBag: false }, add: { _bagExtra: -1 } }) }
   ```
   `hasBag` 在旧档里是 `true` → **选项可见、点得到** → `0 + (-1) = -1`。

> 这与项目 MEMORY §1 的既定规则冲突：**「改字段含义 / 结构（语义变了，补默认值反而错）应把 `SAVE_VERSION` +1 弃档」**。
> 本次改造把 `bagVolume` 从「存数字的普通变量」改成「派生值」，正是"字段含义变了"，属于应当 bump 的情形，但没有 bump。

## 四、为什么能确定"新开局不会出问题"

在真实引擎里跑不变量：

```
新开局：hasBag=false, _bagExtra=0
  → ３个拾取点（安盛街铁柜 / 新达汇2F杂物间 / 安居苑卧室）全部是 set:{hasBag:true}, add:{_bagExtra:1}
  → 所以  hasBag=true  ⇒  _bagExtra >= 1
```

**全库 `_bagExtra` 的写入点只有 4 处**（`core.js:100` 初值、`core.js:357` 计算、`core.js:772` 丢弃、3 处拾取各 +1），没有任何地方裸减。
因此 `hasBag === true` 与 `_bagExtra === 0` **同时成立**，只可能来自「旧档 + 补默认值 0」这一条路径。
→ 你那份档必然是 **09-21 13:00 之前写的**。

自查一行（浏览器控制台）：
```js
({ hasBag: gameState.hasBag, _bagExtra: gameState._bagExtra, _bagTier: gameState._bagTier,
   bagVolume: gameState.bagVolume, itemCount: gameState.itemCount })
```
只要出现 `_bagExtra = -1` 且 `_bagTier = 0`，就已证明这份档来自改造前（新开局不可能产生 -1）。

## 五、影响面（不只这一档）

同一根因还有三张面孔，任何 09-21 之前的旧档都会撞上：

| 旧档实际持有的容器 | 旧档存的容量 | 迁移后容量 | 损失 |
|---|---|---|---|
| 帆布袋 | 4 | 3 | −1，且 `整理整理` 里丢袋子 → `_bagExtra = -1` |
| 双肩包（安居苑 203 室） | 4 | 3 | −1；另因 `hasBag` 残留为 true，`整理整理` 会**凭空多出「丢下帆布袋」**，一点就变 −1 |
| 书包（建平挹芬楼 3F） | 5 | 3 | −2 |

另外，`换包` / `捡书包` 的正文里有 `if (vars.hasBag) base += "帆布袋收紧抽绳挂在包侧……"`（`建平中学.js:3408`、`上实南校.js:110`、`安居苑.js:744`），旧档玩家会读到自己并没有的帆布袋描写 —— 同为 `hasBag` 语义变更的残留。

## 六、修复方案（三选一，需你拍板）

> 取舍焦点：旧档里 `hasBag: true` **分不清**当时拿的是帆布袋还是双肩包 —— 改造前两者共用这一个标志，代码里没有任何可用的判别依据。
> 但**容量数字是可靠的**：旧档把 `bagVolume` 的真实值存下来了（4 或 5）。所以三种方案都能把容量补回去，区别只在"挂到哪个字段"。

| 方案 | 做法 | 结果 | 取舍 |
|---|---|---|---|
| **A（推荐）补写迁移** | `fillMissingDefaults` 里加一条：旧档缺 `_bagTier`/`_bagExtra` 时，按旧 `bagVolume` 反推 —— 4 → `_bagExtra=1`；5 → `_bagTier=2` | 容量精确还原；`hasBag=true` 与 `_bagExtra=1` 重新自洽，**结构性消灭 −1** | 拿双肩包的玩家会被叙述成"帆布袋"（仅 `换包`/`整理整理` 的措辞受影响）；不弃档 |
| **B 只加钳位** | `_caps` 加 `_bagExtra: { min: 0, max: 9 }` | 挡住 −1，但容量缩水仍在（4→3），玩家仍捡不了 | 最省事，但没修好你遇到的那个症状；属"防崩溃"不属"修 bug" |
| **C 按既定规则弃档** | `SAVE_VERSION` → 2 | 旧档全部作废、重开，容量自然正确 | 符合 MEMORY §1「改字段含义应 bump」的既定规则；代价是玩家当前进度全丢（你现在这份档就没了） |

**我的建议：A**。理由是它同时解决了"容量缩水"和"−1 暴涨"两个症状，而且不牺牲玩家进度；B 只治标；C 代价最大。
若你更在意"规则一致性"（宁可弃档也不做语义猜测），那就走 C —— 但那样**当前这份档救不回来**。

方案 A / B 的效果已在复现脚本第 5 组预演（**代码未改，仅算数**）：
```
     方案A（迁移成帆布袋 _bagExtra=1）→ 容量 4，丢袋后 {"bagVolume":3,"_bagExtra":0}
     方案B（_caps 加 min:0，只防负数）  → 容量仍 3（缩水未解）
```

