## 连续移动疲劳台账语义修订（_fatiguePaid 改为随里程归零）

- 用户提出 `_fatiguePaid` 应与 `_travelMinutes` 一起在休息/吃饭/躲藏/过夜时归零，才能体现"连续移动疲劳"。分析后同意：旧版"只增不退、按历史最高档计费"会让疲劳在付过第 5 档后**整局失效**（机制中期名存实亡）；而旧版防的"休息→再走20分钟→又扣"其实不是刷体力漏洞——restRecover 有 REST_CAP=6 上限、小憩消耗游戏时间、饥饿时钟照走，"适时休息躲疲劳"正是设计意图。
- 实现选了单点改法：**不动全库 40+ 归零点**，在 core.js travel-fatigue 规则 effect 开头加 `if (t === 0) { v._fatiguePaid = 0; return false; }`，靠规则在 tier→0 跳变上自动清台账。未来任何新写的归零代码自动正确；规则必须保持无 condition（写条件会让归零后规则被跳过、台账清不掉）。
- Node 模拟回归 7/7 通过：整段 -5、休息重扣第 1 档、同档不重复扣、跨多档一次扣清、读档/回溯不重复扣、付满 5 档后休息再走仍会重新计费。
- 文档同步：core.js 注释（变量+规则）、CLAUDE.md §疲劳系统 + reactive `condition` 字段说明 + 变量表（新增 _fatiguePaid 行）、设计细节.md §连续移动疲劳系统（删除"只增不退"旧描述与"过夜恢复 2 档"钩子，重置方式表补躲藏行）。
- 教训：上一轮"无限刷扣体力"的判断是把正确语义误诊为 bug；防刷应以资源守恒分析为准（扣的是惩罚、回复有上限、时间有成本），而非凭直觉加棘轮。
