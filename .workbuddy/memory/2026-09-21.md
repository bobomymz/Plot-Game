## 环境诊断：Bash 「dirname/ls/python not found」根因确认与解法

**现象**（用户转述此前 AI 反馈）：Bash 里 `dirname` / `ls` / `python` 全部 `command not found`，基本不可用。

**核实结论：属实，但根因不是 PortableGit 装坏了，而是缺 PATH 条目。**

- PortableGit 安装**完整无损**：`C:\Users\wgdin\.workbuddy\binaries\PortableGit\versions\1.2.0\` 下
  `usr/bin`（含 `dirname.exe` / `ls.exe`）、`cmd`、`mingw64` 均在；绝对路径调用 `dirname.exe`、`ls.exe` 正常。
- **真正原因：PATH 里没有 PortableGit 的 `usr/bin`。** PATH 中唯一沾 Git 的是 `D:\Program Files\Git\cmd`，
  而 `cmd` 只有 `git.exe`，**不含任何 coreutils**（ls/dirname/tr/grep/sed/awk/wc/head 全无）。
  系统 `D:\Program Files\Git\usr\bin` 存在但**同样不在 PATH 上**。
- 结果：bash builtin（`echo`/`cd`/`export`/`[` 等）能用，**所有外部命令一律 not found**，node/python 一并失效。
- **附带发现：PATH 格式被污染** —— 原文应为
  `D:\WorkBuddy\resources\app.asar.unpacked\cli\vendor\shim\safe-bin` 的条目，被 `:` 切成了 `D` 和
  `\WorkBuddy\...` 两条（Windows 盘符 `D:\` 被当分隔符）。同源问题：`BASH_ENV` 是 Windows 反斜杠格式
  `D:\WorkBuddy\...\shell-runtime-bash-env.sh`，bash 能打开它，但文件内第 3 行
  `$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)` 因 dirname 不可用而失败，于是**每条命令都往 stderr 打两条噪声**：
  `dirname: command not found` + `cd: null directory`（无害，可忽略）。

**已验证解法**（命令开头 export 即可，不用改任何配置）：
```bash
export PATH="/c/Users/wgdin/.workbuddy/binaries/PortableGit/versions/1.2.0/usr/bin:/c/Users/wgdin/.workbuddy/binaries/PortableGit/versions/1.2.0/bin:$PATH"
```
加完后 dirname/ls/tr/grep/wc/sed/awk/python/python3/date 全部恢复；`node tools/condition_audit.js` 跑通（0/0）。
**操作约定**：本项目里任何需要外部命令的 Bash 调用，开头都先 export 这行，否则一律 not found。

**排查手法备忘**：环境类「工具全 not found」优先怀疑 PATH 而非二进制缺失——用 `[ -e "$p" ]` 逐个探测
绝对路径可快速区分「装坏了」与「没上 PATH」，比 Glob 可靠（Glob 对含中文的 U 盘路径 + 深层目录
返回 No files found，会误导成目录不存在）。

## 追加：用户改系统 PATH 后仍无效 —— 定位到 WorkBuddy 自身 bug（同日 13:17）

**用户操作**：把 `D:\Program Files\Git\usr\bin` 加进系统 PATH，重启 WorkBuddy。
**用户自测**：在**自己打开的 Git Bash** 里全部正常（dirname/ls/grep/tr/wc/sed/awk/date 全 OK；python=3.8.10、node=v25.2.1 ——
注意这是系统 Python38 和系统 node，与 WorkBuddy 托管版本不同，证明那是**另一个进程**）。
**但 WorkBuddy 的 Bash 工具里仍然全部 not found**（python/node 却是好的）。

**根因（已定位到源码）**：`D:\WorkBuddy\resources\app.asar.unpacked\cli\dist\codebuddy.js`
里的 `buildPluginPathEnv()`：

```js
function buildPluginPathEnv(eA){
  let el = process.env.PATH || "";
  if("win32" !== process.platform) return [...eA, el].filter(Boolean).join(":");
  let {shell: ec} = getShellConfiguration();
  if(ec === "bash" || ec === "zsh" || ec === "sh"){
    let toUnix = a => windowsPathToUnix(a);
    return [...eA.map(toUnix), ...el.split(";").filter(Boolean).map(toUnix)].join(":")
  }
  return [...eA, el].filter(Boolean).join(";")
}
```

**缺陷**：Windows 盘符含冒号。`windowsPathToUnix("D:\\Program Files\\Git\\cmd")` 产出 `/d/Program Files/Git/cmd`，
但转换若未完整处理（或含残留反斜杠的段），`join(":")` 后 bash 就会**在盘符的冒号处错切**——
这正是 PATH 开头那两条碎片 `[D]` + `[\WorkBuddy\...]` 的成因（本应是
`D:\WorkBuddy\...\shim\safe-bin` 一条）。**必须用 `/d/...` 开头的 POSIX 路径，不能靠 `windowsPathToUnix` 半吊子转换。**

**实测证据（bash 内 PATTERN 匹配）**：
- `case ":$PATH:" in *"Git/cmd"*)` → **YES**（旧的 `Git\cmd` 进了 PATH）
- `case ":$PATH:" in *"Git/usr/bin"*)` → **NO**（新加的 `Git\usr\bin` 没进）
- PATH 共 38 条，后半段是原样保留的 Windows 风格条目（`/d/Program Files/Python38/` 等带尾部斜杠）
→ 结论：**用户新加的条目在注册表里，但没能通过 `buildPluginPathEnv` 的转换/拼接进入 bash 会话**。

**另注**：`reg.exe` 被安全策略拉黑（Program Blacklist），**不能用 reg query 读 PATH 注册表**；
`PowerShell` 工具的 stdout 在本环境也未被捕获（Exit 0 但无输出）。
→ 读环境变量只能靠 bash 侧的 `case`/`[ -e ]` 探测，别绕道 reg/PowerShell。

**解决方案（按推荐度）**：
1. **最省事且已验证**：脚本/命令开头 export PortableGit 的 `usr/bin`（无空格，转换不会出问题）：
   ```bash
   export PATH="/c/Users/wgdin/.workbuddy/binaries/PortableGit/versions/1.2.0/usr/bin:$PATH"
   ```
   实测 coreutils + python 3.13.14 + node v22.22.2 全恢复，`condition_audit` 0/0。
2. 若想一劳永逸：在 `~/.bashrc` 或 WorkBuddy 的 shell snapshot 里加同一行 export（改的是用户配置，非应用安装目录）。
3. 直接改 `buildPluginPathEnv` 修 bug —— **不推荐**：`app.asar.unpacked` 属应用安装目录，会被更新覆盖。

## ⚠ 最终解法：改 BASH_ENV 指向的 shim 脚本（同日 13:25 落地并验证）✅

**关键坑：`~/.bashrc` 对 WorkBuddy 的 Bash 工具完全无效！**
- 实测 `$-` = `hBc` → **非交互、非登录** shell。bash 只在**交互式**才自动读 `~/.bashrc`，
  所以 WorkBuddy 每条命令都**不会**加载它（已用「写入后新命令仍 dirname not found」实证）。
- 已给用户创建 `C:\Users\wgdin\.bashrc`（内容含 coreutils PATH 前置，带存在性判断和去重），
  **它只对用户手动开的 Git Bash（交互式）有用**；实测 `bash -i -c 'dirname ...'` 生效，普通调用不生效。
- 同理 `etc/bash.bashrc`、`etc/profile` 也都不管用（非登录非交互）。

**真正生效的注入点：`BASH_ENV`。** 非交互 bash 唯一自动 source 的就是它。
WorkBuddy 注入的值 = `D:\WorkBuddy\resources\app.asar.unpacked\cli\vendor\shim\shell-runtime-bash-env.sh`
（该脚本第 3 行 `dirname` 报错，恰好证明它【每次都被执行】）。

**已实施的修复**（文件可写，已先备份为 `shell-runtime-bash-env.sh.bak-20260921`）：
在该脚本**最顶部**（`__codebuddy_shell_runtime_dir=...` 之前）插入：

```bash
__codebuddy_pg="/c/Users/wgdin/.workbuddy/binaries/PortableGit/versions/1.2.0"
if [ -d "${__codebuddy_pg}/usr/bin" ]; then
  case ":${PATH}:" in
    *":${__codebuddy_pg}/usr/bin:"*) ;;
    *) PATH="${__codebuddy_pg}/usr/bin:${__codebuddy_pg}/bin:${PATH}" ;;
  esac
fi
export PATH
unset __codebuddy_pg
```

**验证结果（无需任何手动 export）**：dirname/ls/grep/tr/wc/sed/awk/date/python/node 全部可用，
且 **stderr 两条噪声（`dirname: command not found` + `cd: null directory`）彻底消失**——
因为 PATH 修好后，脚本第 3 行的 `$(cd "$(dirname ...)" && pwd)` 终于能正常执行。
注意：**必须插在第 3 行之前**，否则第 3 行仍会在 PATH 修好前执行而报错。

**项目回归全绿**：condition_audit 0/0、unarmed_fight 34/34、bag_volume 33/33、
stamina_telemetry 9/9、stamina_report --selftest 22 条。

**⚠ 持久性风险**：该文件在 `app.asar.unpacked`（应用安装目录），**WorkBuddy 更新后可能被覆盖**。
